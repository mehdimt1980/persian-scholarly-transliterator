# Phase 8F — MARC linkage validation

The parser now uses the namespace-aware `saxes` XML parser rather than regular expressions. It accepts MARCXML default or prefixed namespaces and preserves repeated control/data fields, field order, namespace URIs, both indicators, and ordered subfields. It rejects DTDs, processing instructions, malformed XML, incorrect roots/namespaces, and unexpected MARC structure; `saxes` does not resolve external entities. Explicit limits cover response bytes, nesting depth, element count, text size, record count, fields per record, and subfields per field. SRU version, counts, record positions, next position, and diagnostics are validated and surfaced explicitly.

An 880 is linked only when its `$6` has `TAG-NN` and exactly one corresponding base field has `880-NN`. Script suffixes such as `/(3/r` are preserved but do not alter occurrence matching. Missing or duplicate/contradictory matches remain visible as `UNCERTAIN_VARIANT` evidence and do not produce a linked romanization. Phase 8F supports linkage for 100, 110, 245, 700, and 710; 111 and unrelated 880 content remain preserved by the parser but are not promoted to candidates.

For an original-script 880 linked to a Latin 245, the Latin value is a `ROMANIZATION_CANDIDATE`, not a verified IJMES form. MARC 246 second indicator 1 is preserved as `PARALLEL_TITLE` provenance and represented in the existing candidate classification as `UNDETERMINED_LATIN_VARIANT`; it is not asserted to be a translation. `TRANSLATED_TITLE` requires separate explicit relationship metadata, which these records do not provide. The authentic records `991071006889707356` and `991144600686807356` validate 245/880 and 710/880 linkage. Arabic-script records lacking Persian language metadata fail closed and yield no candidate.
