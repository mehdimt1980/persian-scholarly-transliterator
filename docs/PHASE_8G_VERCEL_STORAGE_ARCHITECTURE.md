# Phase 8G — Vercel storage architecture

The operational path is authentic BSB fixture → `prepareBsbPublication` → guarded private Vercel Blob content-addressed archive → guarded Neon record versions and candidate projections → validated transactional snapshot publication → a new PostgreSQL reader instance → existing `LexicalEvidenceIndex` semantics. `importBsbEvidencePersistent` composes these pieces; it runs database preflight before the first Blob write. Blob and database clients exist only under `src/server`; no browser or public ingestion route is provided.

Read-only inspection on 2026-10-09 found that Preview and Production receive identical `DATABASE_URL`, `POSTGRES_URL`, `NEON_PROJECT_ID`, and `BLOB_STORE_ID` values. They therefore share the currently connected Neon target and private Blob store. No migration or import was run. The write guard rejects this `SHARED_OR_UNKNOWN` topology. Preview must receive a distinct Neon branch or schema and isolated Blob prefix before writes.

Required server-only names are listed in `.env.example`. The database fingerprint is SHA-256 over the lower-case connection hostname, `current_database()`, `current_user`, and `current_schema()`, joined in that order with newline characters. Authorization requires that read-back identity to match `EVIDENCE_DATABASE_FINGERPRINT` and a matching row in `evidence_environment_binding`. Blob writes compare the connected `BLOB_STORE_ID` with the independently approved `EVIDENCE_BLOB_STORE_ID`. Configuration flags alone are insufficient. Values and connection strings must never be logged.

The path is unit-tested and has an opt-in real integration suite. It has not been executed against Neon or Blob because no isolated authorized target is configured; real integration verification is therefore **BLOCKED**, not passed.
